# Step 18: Real-time top-of-book overlay

The skeleton's streams are **conflated**. Binance's `depth20@100ms` sends a snapshot at
most every 100 ms, whatever happened in between. For the best bid and ask, the prices
traders act on, both venues offer a faster stream:

- **Binance `bookTicker`**: every change to the best bid or ask.
- **Bybit `orderbook.1`**: the top level every 10 ms.

This step subscribes to those streams on the same connection, **reconciles them with the
depth book by sequence number**, and publishes the fresher top over the depth.

**Measured on 59 s of live data:** without this, Binance's published best bid and ask
were **wrong 66% of the time**, typically **52 ms old** (exchange time) and up to 108 ms
old. With it, they're current.

## 1. First, find out what the streams really do

Before designing anything, I recorded 15 s of both streams on one connection per venue,
using our own client from step 12 (the installed Python `websockets` was too old for this
Python version). Then I checked the property the design depends on: **are the sequence
numbers comparable across the two streams?**

| | Binance | Bybit |
|---|---|---|
| Rate: depth vs top | 10/s vs **~800–1,265/s** | 45/s vs 46/s |
| Top-of-book form | `bookTicker`: one bid and one ask, as price/quantity strings | `orderbook.1`: always `"type":"snapshot"` (verified: no deltas in 561 messages) |
| Sequence used | `u` (order-book update ID) | `seq` (Bybit's "cross sequence") |
| Check at every depth message: does the latest top with sequence ≤ the depth's show the same best prices? | **143 / 143 identical** | 617 match, 28 differ |

- **Binance is proven:** `bookTicker.u` and depth's `u` are one sequence. The top as of
  update *u* is identical in both streams.
- **Bybit's 28 differences are expected.** `orderbook.1` is sampled every 10 ms, so when
  depth's `seq` is higher the book has moved since. The rule "the higher `seq` wins"
  handles that correctly. Bybit documents `seq` as comparable across order-book depths.

## 2. Parsing

### Binance: one parser, two shapes for the same keys

`b` and `a` are **arrays of levels** in depth but **price strings** in `bookTicker`. The
parser is field-order independent (step 6), so it can't wait for `e` to say which form
to expect. It looks at the value's first character:

```rust
Field::Bids if c.peek() == Some(b'"') => { bids_str = true; bid_px = self.price(&mut c, field)?; }
Field::Bids => self.levels(&mut c, &mut out.bids, field)?,
```

At the end it checks the shape matches the event: arrays for `depthUpdate`, strings for
`bookTicker`; a mismatch is `BadLevel`. A ticker is small, so it is returned by value
(`Message::BookTicker(BookTicker)`) rather than through the depth buffer.

### Bybit: a second topic

`BybitBookParser::with_top_topic(b"orderbook.1.BTCUSDT")` accepts either topic and records
which in `BookMsg::channel`. Any other topic is still `WrongTopic`.

### The same rigour as steps 6–7

- **The serde_json oracles implement the new rules independently,** and the differential
  tests cover recorded frames, mutated frames (now 120 per venue) and generated messages
  (now including complete tickers and top-topic messages).
- **The quality guard caught a weak generator.** At first only 2 in 2,000 generated Bybit
  messages were valid top-of-book messages, so that path was barely tested. The
  generator now picks the topic too (221 in 2,000), and Binance produces 525 valid
  tickers in 2,000. Both counts are asserted.
- The fuzz targets share these oracle files and still compile; their signatures are
  unchanged, and the new functions are `_with_top` variants.

## 3. Publishing an overlay without touching the book

```rust
pub fn publish_with_top(&mut self, book: &OrderBook<CAP, S>, top: Option<TopOverlay>, meta: BookMeta)
```

Per side, readers see **the overlay's level first, then only the book's strictly worse
levels**:

```text
book (older, u=100):   bids 100 99 98         overlay (newer, u=105): bid 99 (qty 7)
published:             bids 99(qty 7) 98       ← 100 was traded through; 99's qty is newer
```

- **Book levels at or better than the overlay's price are stale.** The overlay proves
  the book has moved past them: traded through, cancelled, or (at the same price) their
  quantity changed.
- **Deeper levels are kept.** The overlay says nothing about them, and they're the best
  information there is. Readers of depth know it's ≤ 100 ms old (`exchange_ts`).
- **The book itself is never modified.** That's essential for Bybit: its deltas must
  keep applying to exactly the state the venue described. Writing the overlay into the
  book would corrupt every later delta. The overlay exists only in what readers see.
- **No copy.** The merge happens while writing into the seqlock (a `skip_while` over the
  book's levels). Plain `publish` now calls `publish_with_top(book, None, …)`, and the
  benchmark shows no slowdown (20×20: −5.6%, 50×50: no change).
- **A property test** checks every published book against a direct model: the overlay
  level, then the book's levels filtered by "strictly worse", truncated to `DEPTH`.

## 4. Reconciliation: the newest sequence wins

Each venue keeps the depth book plus `top: Option<(sequence, TopOverlay)>`:

| Event | Rule |
|---|---|
| Top-of-book message, no depth book yet | **Ignored.** Two prices are not a book, and the venue must not go Live on them. |
| Top-of-book message, sequence ≤ the newer of book and overlay | **Ignored:** old news (arrived late or out of order). |
| Top-of-book message, crossed (bid ≥ ask) | **Rejected.** Never seen live, never trusted. |
| Top-of-book message, newer | Becomes the overlay; publish (`Applied { top: true }`). |
| Depth message applied, sequence ≥ the overlay's | **Overlay dropped:** the book has caught up. |
| Reset (resync, reconnect) | Overlay dropped with the book. |

`FeedStats::top_updates` counts overlay updates separately from depth.

### Tests

1. **Differential on recorded data.** Two feeds get the same interleaved stream, one
   depth-only and one with the overlay. After every message, the overlay feed's
   published book must equal the model: the depth-only book plus the newest top whose
   sequence is higher.
   - Binance: 1,000 messages; 992 overlays, 3 superseded by depth.
   - Bybit: 150 messages; 63 overlays, 46 superseded.
   - It's never crossed.
2. **A test bug worth knowing.** My first Bybit version also fed `orderbook.1` lines to the
   depth-only feed. That connection never subscribed to the topic, so it correctly treated
   the message as unparseable and resynced, which emptied the reference book. The
   reference feed now sees only what it would really receive.
3. **Mutation testing found two rules the recorded data couldn't test:**
   - "Depth never clears the overlay" passed.
   - "Accept Bybit tops older than the book" passed.

   The reason is that **real data is self-consistent**. When depth catches up with an
   overlay, the overlay's prices *are* the depth's top (the 143/143 result), so a stale
   overlay publishes the same numbers. And in the fixture every Bybit top happened to be
   newer. I added **synthetic sequences built to disagree**: a newer depth with a
   different top, older tickers arriving late, a crossed ticker. Both mutations now
   fail. A third mutation (reset keeps the overlay) was caught from the start.
4. **Zero allocations** on the overlay paths: 999 Binance and 149 Bybit interleaved
   messages, 0 allocations.

## 5. Measured live (60 s, `ob live --latency --record`)

### Freshness: the point of the step

These numbers compare **exchange timestamps with each other**, so they're immune to clock
skew (see below).

| | Binance | Bybit |
|---|---|---|
| Depth-only best bid/ask differs from the reconciled one | **65.8%** of 75,038 samples | 4.2% of 5,364 |
| How much older the depth-only top is: p50 / p90 / p99 / max | **52 / 91 / 101 / 108 ms** | 0 / 12 / 32 / 112 ms |

- **Binance:** a large win. The 100 ms conflation shows directly: the age is spread
  across 0–108 ms with a median of about half the interval.
- **Bybit:** a small win. Depth already arrives every 20 ms; it's almost free, so it's
  kept.

### Cost

| | Binance | Bybit |
|---|---|---|
| Messages in 60 s | 75,104 (74,462 tickers) | 5,382 (2,673 tops) |
| Handle (parse+apply), live p50 / warm replay p50 | 372 ns / 299 ns | 2,565 ns / 444 ns |
| Publish, live p50 / warm replay p50 | 105 ns / 91 ns | 403 ns / 224 ns |
| Read stage p50 / p90 | **84 ns** / 29 µs | 35 µs / 74 µs |

- **Binance's read median fell from ~45 µs (step 16) to 84 ns.** At about 1,265 messages
  per second, several messages often arrive in one TLS record, so most `poll()` calls
  return a message already buffered, with no system call. The p90 (29 µs) is the real
  reads.
- **CPU cost:** about 1,265 × ~0.5 µs ≈ 0.06% of a core. Trivial.
- **Replay** reproduces the live counts exactly (75,038 applied, 74,462 top of book), and
  two replays give identical final books. It runs at 1.7 million records/s.

### The correction this step forced (appended to step 16's note)

The live latency table showed exchange → us at **7.4 ms (Binance) and 1.0 ms (Bybit)**,
against step 16's ~43 ms, from the same place an hour later, with 60 negative values on
Bybit. A 1 ms one-way delay from Singapore isn't physically plausible, so I checked:

- `sntp`: this laptop's clock was **113 ms off**, more than the delays being measured.
- Round-trip times, which need no clocks (TCP connect): **Binance 234–244 ms**, **Bybit
  7–10 ms** (its WebSocket ends at a nearby edge server).
- Consistent: 7.4 + 113 ≈ 120 ms ≈ half of Binance's round trip.

So step 16's "exchange → us ~43 ms" measured clock skew, not the network. Its conclusion
(the network dominates by thousands of times) stands, now on sound numbers: a 234 ms
round trip against ~50 µs in-process. This is why the freshness numbers above compare
exchange timestamps with each other rather than with our clock.

## 6. What this step deliberately doesn't do

- **Overlaying when the depth book is missing.** Tickers before the first depth snapshot
  are ignored: two prices aren't a book.
- **Trades** (`aggTrade`, `publicTrade`): a further freshness signal (a trade at the bid
  proves the bid was hit), but it can't be reconciled by sequence as cleanly. Noted.
- **Binance full depth** (diff stream plus REST snapshot): step 19, optional.

## 7. Java counterpart

The skeleton subscribes only to the conflated streams and prints from them. It has no
notion of the top being stale.

A Java version would subscribe both streams on one client (Java-WebSocket's `send` of a
two-stream `SUBSCRIBE`), dispatch on `"e"` after parsing to a tree (`JsonNode`), and keep
the overlay in a field, e.g. `volatile BookTicker top`. Two things to watch:

- **Publication must be atomic.** Readers must never see the new overlay with the old
  book, or the reverse. With `synchronized` that means the reader locks too; with a
  seqlock-like `StampedLock` optimistic read it's close to ours.
- **The rate.** 1,265 messages per second through Jackson and `BigDecimal` is
  ~1,000+ allocations per second per venue: garbage-collector pressure that our parser
  avoids (0 allocations, proven).

```java
switch (node.get("e").asText()) {
    case "bookTicker" -> { long u = node.get("u").asLong(); if (u > newestU()) top = parseTicker(node); }
    case "depthUpdate" -> { applyDepth(node); if (top != null && top.u() <= lastU) top = null; }
}
```

## Likely interview questions

1. **Why is the depth stream's best price wrong so often?**
   It's conflated to 100 ms: a snapshot of the state at send time. BTCUSDT's top changes
   ~1,000 times a second, so between snapshots the published top is stale. Measured:
   wrong 66% of the time, 52 ms old at the median.
2. **How do you combine two streams safely?**
   By the venue's own sequence number, never by arrival time. Binance's `bookTicker.u`
   is the same order-book update ID as depth's `u`; I verified it on 143/143 messages.
   Bybit's `seq` is documented as comparable across depths. The newer one wins, and an
   older one is ignored even if it arrives later.
3. **Why not just write the ticker into the order book?**
   For Bybit that corrupts the book: later deltas would apply to a state the venue never
   had. The overlay lives only in the published view; the book stays exactly as the
   venue described it, and the merge costs nothing extra because it happens during the
   seqlock write.
4. **What do you do with the depth levels behind a newer top?**
   Drop the ones at or better than the new top (proven stale) and keep the deeper ones
   (no newer information, and still at most 100 ms old).
5. **Your tests passed with the reconciliation rule deleted. How did you find out, and
   what did you do?**
   Mutation testing. Real data is self-consistent: when depth catches up, the overlay's
   prices equal depth's top, so a stale overlay is invisible. Synthetic sequences built
   to disagree now pin each rule. Lesson: recorded data tests the common case;
   adversarial cases need constructed inputs.
6. **How did you measure "freshness" without trusting your clock?**
   By comparing the venue's timestamps with each other (depth's `E` vs the ticker's `E`).
   This step also showed my earlier exchange → us latency was mostly clock skew: the
   laptop clock was 113 ms off. One-way latency needs synchronised clocks (PTP); a round
   trip doesn't.
